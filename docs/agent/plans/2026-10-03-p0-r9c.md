# Plan 2026-10-03 — P0-r9c: PR-6 unified mass

## Problem

`PositionAssigner` groups bars by a `PositionKey` whose `RoundedLengthMm` is an `int`
(bar length rounded to the nearest mm). It then computes schedule mass from that rounded
figure, not from the precise `TotalLength` stored on each `RebarSegment`.

For bars whose exact length ends in a non-zero fraction the schedule CSV and the
`result.json` certificate disagree. For the simple-slab example:

| Source | Length used | Total mass (27 bars, Ø20 A500C) |
|--------|-------------|----------------------------------|
| `result.json` | 6565.49 mm (exact) | 437.852 kg |
| `schedule.csv` (before) | 6565 mm (rounded) | 437.820 kg |
| `schedule.csv` (after) | 6565.49 mm (exact) | 437.852 kg |

Drift = 0.032 kg (0.007 %). Harmless in isolation, but breaks the invariant that
certificate totals equal schedule totals.

## Fix

In `PositionAssigner.Assign`, replace:
```csharp
double massPerPiece = ReinforcementLimits.GetLinearMass(key.DiameterMm)
    * (key.RoundedLengthMm / 1000.0);
```
with:
```csharp
double exactTotalLengthMm = group.Sum(item => item.Rebar.TotalLength);
int count = group.Count();
double linearMass = ReinforcementLimits.GetLinearMass(key.DiameterMm);
double totalMassKg = linearMass * exactTotalLengthMm / 1000.0;
double massPerPiece = totalMassKg / count;
```

The grouping key and `LengthMm` column remain `RoundedLengthMm` (int), so the
catalogue length and position name are unchanged.

## Test

Add `PositionAssigner_TotalMassUsesExactLength` to `PositionAssignerTests`:
create a zone with bars whose exact length has a 0.49 mm fractional tail, assert
`TotalMassKg ≈ linearMass × exactTotalLength / 1000` within 1e-6 kg.
